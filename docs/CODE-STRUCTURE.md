# 改枪码结构分析：为什么「指纹」不是特征

这份文档记录一个重要的技术事实，避免以后再误以为「前 10 位指纹」是枪械特征。

## 结论

**改枪码本体里不编码枪械信息。** 规则库本质上是「完整码 → 枪名」的查表，
覆盖面 = 收录过的码，**对没见过的纯码没有任何泛化能力**。

> ⚠️ **重要区分（v1.8.0 补充）**：本节说的是**码本体**那 21 位随机串。
> 而游戏/文档里的**标准格式**是 `<枪名>-<模式>-<码>`，枪名是**人工标注**在前缀里的，
> 可以直接解析 —— 那不是推断。详见文末「标准格式前缀」一节。

## 证据

分析脚本：`scripts/analyze-code-structure.mjs`、`analyze-fingerprint-nature.mjs`、
`analyze-segment-power.mjs`（样本 = 本机 553 + anxu 1702，共 2255~2407 条，619 个批次）。

### 1. 同一把枪的码之间几乎没有公共前缀

| 枪 | 样本数 | 公共前缀长度 |
|---|---|---|
| M7战斗步枪 | 93 | **1 位** |
| RM277突击步枪 | 93 | **1 位** |
| SVCH精确射手步枪 | 77 | **1 位** |
| M14射手步枪 | 70 | **1 位** |
| KC17突击步枪 | 63 | **1 位** |

- 有 ≥3 条样本的枪共 **121 把**，平均公共前缀 **1.10 位**
- 其中前 10 位相同的：**0 把**

> 如果前 10 位真是枪械特征，同一把枪的多个码应该共享它。事实是连第 2 位都不共享。

### 2. 逐位置的字符对枪名毫无区分力

对码的每个位置，统计「该位置字符 → 枪名」的纯度（最常见枪名占比）：

| 位置 | 取值数 | 平均纯度 |
|---|---|---|
| 0 | 1 | 4.5% |
| 1 | 8 | 8.0% |
| 2 | 32 | 11.3% |
| 3 | 32 | 8.8% |
| … | … | 4.5%–36% |

全部 21 个位置的纯度都在 **4.5%–36%**，接近随机猜测。没有任何一个位置携带枪械信息。

### 3. 高纯度片段都是「唯一 ID」，不是特征

滑动窗口枚举所有长度 3–8、所有起始位置：

| 片段 | 纯度 | 唯一值数 | 能预测的样本数 |
|---|---|---|---|
| 2-9 | 99.9% | **2200** | **0** |
| 3-10 | 99.9% | **2200** | **0** |
| 1-9 | 99.9% | **2200** | **0** |

纯度 99.9% 看着很高，但**唯一值数 ≈ 样本数（2200/2202）**，
且「能预测的样本数 = 0」—— 意味着每个片段值几乎只出现一次，
它标识的是「这一个具体配置」，不是「这把枪」。

### 4. 跨批次验证排除了「批次巧合」

按码的后 12 位分组得到 619 个批次。只保留「同一把枪出现在 ≥2 个批次」的样本
（123 把枪、2202 条）后重新枚举，结论不变：**找不到任何能跨批次预测枪名的片段**。

## 这对实现意味着什么

### 现状（v1.4.0）

- `extract_fingerprint()` 取前 10 位当 key，查 `rules.json` 的表
- 行为上等价于「记住见过的码」：见过的能认对，没见过的一律「未知枪械」
- 交叉验证实测：第三方 152 条独立样本里，**命中率仅 19.1%**（29/152）

### 这是**正确**的设计，不是缺陷

因为码里没有特征可用，所以：

1. **扩大覆盖面只能靠「多收录码」**，不能靠「推断规律」
2. 遇到没收录的码时，诚实显示「未知枪械 + 让用户手动填」比猜一个更安全
3. 用户手动填后会被学习表记住 —— 这是唯一能提升覆盖的机制

### 所以真正有价值的三件事

| 机制 | 作用 |
|---|---|
| **规则库在线热更** | 让别人已经收录的码流到你这里（覆盖面靠共享扩大） |
| **学习表** | 你自己遇到的码，填一次就永久记住 |
| **导入预览** | 批量导入时逐条确认，把新码一次性喂进学习表 |

## 如果以后想提升泛化能力

唯一可能的突破口是**码之外的信号**，例如：

- 码在游戏内的「枪械 ID」字段（如果有官方接口）
- 改枪码的**生成时间戳/版本**与枪械赛季的关联
- 依赖官方 API 反查（若存在）

在拿到这类信号之前，任何声称「能推断未知码属于哪把枪」的做法都是不可靠的。

node scripts/analyze-fingerprint-nature.mjs  # 同枪公共前缀

## 标准格式前缀：唯一可「解析」的信号

v1.8.0 补充。前面的分析证明了**码本体无特征**，但改枪码在游戏与文档里通常写成：

```
M7战斗步枪-烽火地带-6KQGVM0016OGGUAER4S67
└── 枪名 ──┘ └─ 模式 ─┘ └──── 码 ────┘
```

枪名**就写在里面**。解析它属于「直接读取」，与「推断未知码」是两件事。

### 实测收益（第三方独立样本 152 条，未参与规则库构建）

| | 仅查表 | 加前缀解析 |
|---|---|---|
| 能认出 | 29 / 152 = **19.1%** | 152 / 152 = **100%** |
| 只有前缀能救回 | — | **123 条** |
| 与查表结果冲突 | — | **0 条** |

### 一个必须同时修的 bug

`extract_fingerprint()` 原本直接对**原始输入**过滤非字母数字，导致：

```text
输入    M7战斗步枪-烽火地带-6KQGVM0016OGGUAER4S67
旧指纹  M76KQGVM00   ← 前缀被压进指纹
新指纹  6KQGVM0016   ← 与规则库一致
```

而规则库构建时（`scripts/build-rules.mjs`）是**先剥前缀再算指纹**的，
所以库里全部指纹（当前 2332 条）都是以 `6` 开头的纯码指纹。两边算法不一致 →
用户粘贴标准格式时永远查不到表。

修正后带前缀与不带前缀算出**同一指纹**。
本机 543 条数据全部是纯码，**零迁移成本**（已实测确认）。

### 识别优先级

```
1. 学习表（10 位指纹）      ← 用户确认过，最可信
2. 规则库（10 位指纹）
3. 标准格式前缀解析          ← v1.8.0 新增，置信度 0.95
4. 旧版 6 位学习表降级       ← 猜测，置信度 0.7
5. DELTA- 格式兜底
```

前缀排在第 3 位而非第 1 位，因为：
- 学习表/规则库是「这个码被确认过是 X」，比手写前缀更可靠
- 但前缀远比「6 位降级匹配」可信

**约束**：前缀解析出的枪名必须能在别名索引命中，否则返回「未知」——
宁可认不出，也不塞一个不存在的枪名。非烽火地带的模式一律拒绝。
